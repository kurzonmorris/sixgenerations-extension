What “needs” means. Some stages wait on an answer from you; some wait on finding something out from a live website, which cannot be guessed from documentation. Those are marked, because they are the ones that stall.

Stage A — Answer the questions that block screens

What it is for. Nothing is built in this stage. It removes the guesswork from every stage after it.

Why now. Four screens cannot be designed without decisions only you can make. Each one in part 1 offers Claude decides, so this can be as short as saying “you choose”.

What gets built

  • Q51 — may the Table have in-place editing (JavaScript)?
  • What the dashboard shows, and where the technical Status block goes
  • What the Boxes page is for
  • Whether a page for one garment should exist (and so where history lives)
  • Whether the five years of old books get imported

Files it touches

  • docs/OPEN_QUESTIONS.md
  • docs/INTERFACE_LAYOUT.md

How we know it works

Every orange block in part 1 has an answer written next to it.

What it waits on

You. Reading part 1 and saying yes, no, or “you choose”.

Stage B — The dashboard — make the first screen about the work

What it is for. Replace the technical Status page as the first thing you see.

Why now. The first screen is the one seen most. Today it is about the server; it should be about today's work. It also needs nothing new underneath — every count already exists.

What gets built

  • Needs fixing at the top (U-15): failed copies, double sales, dead connections
  • Today: to review · to post · ready to list, each a link with the filter set
  • The counts: on sale, never listed, sold this month
  • Items listed per day (X-09) — the number the project is judged on
  • Move the technical block to SYSTEM

Files it touches

  • sixgenbot/modules/dashboard/ (new)
  • sixgenbot/core/itemQuery.py (counts)
  • sixgenbot/modules/systemStatus/ (moves off /)

How it fits the rest

Reads only. Every number is a query that already exists in itemQuery; the links carry the same filter names the Table already understands.

How we know it works

Counts match The Table with the same filter set. Nothing moves on its own. A dashboard with nothing wrong still shows the block, with one line.

What it waits on

Stage A, question 1 and 2.

Stage C — One garment, and its history (U-18)

What it is for. A page for a single garment, with every change it has ever had.

Why now. Every list wants somewhere to click through to, and there is nowhere. The history rows are already being written by every edit, every Vinted read and every photograph move — this is only the screen that reads them.

What gets built

  • Everything the garment says now, every field
  • Its photographs in order, with the reorder link
  • Where it is listed: Vinted, eBay, the shop
  • Its history: every change, what it was before, who did it and when
  • Links out to edit it, to Ready to list, to the box it is in

Files it touches

  • sixgenbot/modules/itemPage/ (new)
  • the event table (already filled)
  • every existing table gains a link to it

How it fits the rest

Pure read, except the links out. The event table already records actor (user / vinted / system), field, value before and value after.

How we know it works

An edit made on the To review screen appears in the history within the same minute, with its old value. A Vinted read appears as actor “vinted”.

What it waits on

Stage A, question 4.

Stage D2 — Listing by hand, faster

What it is for. A person lists on Vinted. The system makes every answer one press away.

Why now. This replaces stages D, E and F. It is the only thing left that moves the 3-to-6-a-day number.

What gets built

  • <b>A</b> — one-press copy beside every field on Ready to list, photographs as a zip. No automation at all
  • <b>B</b> — tick ten garments, the extension opens ten Vinted sell tabs, a panel beside each gives the answers in order
  • <b>C</b> — as B, but the boxes are filled in for you. You add photographs, check, submit
  • Record which garments went up, so they leave the waiting list

Files it touches

  • sixgenbot/core/listingSheet.py (already produces every answer)
  • sixgenbot/modules/listingHelper/
  • source/ (B and C only)

How it fits the rest

A needs nothing new — listingSheet already assembles every answer. B adds tab opening. C adds form filling, and needs the live sell form read first.

How we know it works

Ten garments listed in one sitting, timed against doing it unaided.

What it waits on

Q53 — A, B or C. C is a risk only you can decide to take.

Stage G — The ledger — sales, purchases, totals

What it is for. The money side, matching the existing books exactly.

Why now. Everything about the garment is built; nothing about what it cost or made. docs/EXISTING_LEDGER.md has five years of real numbers to check against.

What gets built

  • Record a sale against a garment, with fees and postage
  • Record a purchase as a lot, sharing cost across its garments
  • Petrol in the profit sum, exactly as the sheet does it
  • A monthly export shaped like the old sheet
  • Import the five years of old books, read-only

Files it touches

  • sixgenbot/modules/ledger/ (new)
  • the salesOrder, lot, purchase, postingTrip tables (all already in the database)
  • sixgenbot/core/csvExport.py

How it fits the rest

The tables exist and are empty. A sale read from Vinted (stage H) fills them automatically; before that they are filled by hand.

How we know it works

A month imported from the old sheet totals the same to the penny. If it does not, the import is wrong.

What it waits on

Stage A, question 5. The petrol price per litre.

Stage H — Sales and orders read from Vinted

What it is for. A sale on Vinted appears here without being typed.

Why now. Removes the main piece of daily typing, and makes To post possible.

What gets built

  • Read sold listings and buyer details in the signed-in session
  • Match to the garment by its listing number
  • Fill the sale record: price, postage, fees where Vinted says
  • Never estimate a fee — NULL means “not told”, not zero

Files it touches

  • source/contentScripts/vintedPageReader.js (the orders endpoints)
  • sixgenbot/core/vintedRead.py
  • sixgenbot/modules/ledger/

How it fits the rest

Depends on stage G for somewhere to put the numbers, and on linking for the match. Buyer details are personal data — docs/DATA_MODEL.md §6.

How we know it works

A real sale appears with the right garment, the right money, and nothing guessed.

What it waits on

Stage G. Investigation of the Vinted orders pages.

Stage I — To post, and the Boxes page

What it is for. The two screens that make the daily round easier.

Why now. Both are named in the layout and both are small once the data behind them exists.

What gets built

  • To post: what is sold and waiting, where it is, one Posted button
  • A parcel photograph kept against the sale
  • Boxes: pick a column, pick a box, see what is in it and which numbers are free

Files it touches

  • sixgenbot/modules/posting/ (new)
  • sixgenbot/modules/boxes/ (new)
  • sixgenbot/core/sku.py (SQL_ORDER, already correct)

How it fits the rest

To post reads the sale records from stage H. Boxes reads only the SKU, so it could in fact be built at any time.

How we know it works

A sale marked posted leaves the list and keeps its photograph. Boxes agrees with the real shelf for one column, checked by hand.

What it waits on

Stage H for To post. Stage A, question 3 for Boxes.

Stage J — eBay, read only

What it is for. See what is on eBay, and answer Q16 with real data.

Why now. Reading cannot damage anything, and it settles whether eBay listings carry the storage code — which decides how everything after it works.

What gets built

  • Connect by API from the server, not the browser
  • Read every listing
  • The three-way list: here, Vinted, eBay
  • Answer Q16 properly

Files it touches

  • sixgenbot/modules/ebaySync/ (new)
  • docs/PROJECT_INFO.md §3 (unverified — <b>check every line against the live API</b>)

How it fits the rest

Same shape as the Vinted read: arrive, plan, apply. The same linking problem, and the same rule — a read never writes over a correction.

How we know it works

The listing count matches what eBay's own page says.

What it waits on

eBay developer keys. PROJECT_INFO §3 is unverified and must be checked first.

Stage K — eBay writes, and sold-anywhere-removes-everywhere

What it is for. The payoff: one garment sells, and it comes down everywhere else.

Why now. This is the thing a cross-listing tool is for, and it is the last big piece.

What gets built

  • Write price and stock to eBay
  • End an eBay listing when it sells on Vinted, and the reverse
  • The shop kept in step too
  • Dry run first, every time

Files it touches

  • sixgenbot/modules/ebaySync/
  • sixgenbot/modules/vintedSync/
  • the existing Shopify writes in the extension

How it fits the rest

Needs every read working and every listing linked. A double sale is the thing this prevents — and the thing that goes on the dashboard when it happens.

How we know it works

A test garment on all three, sold on one, gone from the other two within one run.

What it waits on

Stages D, F and J.

What is already done

224 features are built and working — part 3 lists every one. In short: the database, the import of 2,125 garments, all 9,098 photographs brought off Crosslist, the Table, To review with batch editing, Ready to list, and reading the Vinted wardrobe back in.

The one number that matters. 3 to 6 garments go up a day, against 972 waiting and about 4.6 bought a day. Stage F is the only stage that changes that number — everything before it exists to make stage F safe.
